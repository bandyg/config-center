## 1. 项目背景与定位

### 1.1 业务背景

目前几十台 Kiosk 投注终端每台本地运行着 `config-serv` 服务管理各自配置。运维人员要修改配置时，只能 SSH 到每台机器手动修改，效率极低且容易出错。CTC 系统只面向操作员，无法方便地查看、对比、批量修改各终端的配置。

### 1.2 项目目标

在管理服务器上搭建统一的 **Kiosk Config Center**，通过 HTTP 代理各终端 config-serv 的 API，提供集中管理和 Web UI。

### 1.3 核心价值

| 价值 | 说明 |
|------|------|
| **效率提升** | 从逐台 SSH 操作变为浏览器统一管理，将单次批量操作从小时级降至分钟级 |
| **降低出错率** | 统一配置入口，避免人工逐台操作时的手误和遗漏 |
| **可视化透明** | 在线/离线状态、配置版本号、多终端对比差异，运维状态一目了然 |
| **审计可追溯** | 操作有记录，变更可追溯（后续迭代） |

### 1.4 当前状态

- 项目已开发完成 **Phase 1-4**，所有核心功能可运行验证
- 技术栈：FastAPI + Jinja2 + HTMX（零前端构建）
- 部署形态：PyInstaller 打包为单文件 EXE，双击运行
- GitHub Actions 自动构建 Windows EXE

### 1.5 技术架构概要

```
用户浏览器 → Config Center (FastAPI :8300) → httpx → 各终端 config-serv (:8081)
```

## 3. 用户需求文档（待评审）

### 3.1 目标用户画像

| 角色 | 使用频率 | 核心诉求 | 技术背景 |
|------|---------|---------|---------|
| 现场运维工程师 | 每日 | 快速查看终端状态、修改单机配置 | 低 |
| IT 系统管理员 | 每日 | 批量配置推送、终端集群管理 | 高 |
| 配置审计人员 | 每周 | 配置一致性核查、差异分析 | 中 |
| 开发测试工程师 | 每日 | 频繁修改配置验证、异常测试 | 高 |
| 门店运营主管 | 偶尔 | 全局状态概览、配置异常识别 | 低 |

### 3.2 功能性需求（按优先级排列）

#### F1: 配置编辑体验升级（P0）
**用户诉求：** 当前 JSON 纯文本编辑体验差，大面积 JSON 难以定位字段，容易出错。

**需求描述：**
- F1.1 编辑器支持语法高亮、行号显示
- F1.2 支持树形展开/折叠浏览 JSON 结构
- F1.3 支持一键 JSON 格式化/美化
- F1.4 支持字段搜索定位
- F1.5 非法 JSON 提交时精确定位错误行/列
- F1.6 编辑区域可根据内容自适应高度或全屏模式

#### F2: 操作反馈与安全增强（P0）
**用户诉求：** 保存操作缺乏安全感，无确认弹窗、无变更预览、无进度指示。

**需求描述：**
- F2.1 保存/推送前弹出确认对话框，显示操作摘要
- F2.2 批量推送展示实时进度条（当前终端/总终端数）
- F2.3 推送前显示「当前值 vs 新值」差异对比
- F2.4 推送完成后显示成功/失败清单及失败原因
- F2.5 保存按钮防重复提交（提交后立即 disabled）
- F2.6 推送操作支持取消/中断

#### F3: 批量操作交互重构（P1）
**用户诉求：** 分组/终端选择逻辑反直觉，配置项列表无分类说明。

**需求描述：**
- F3.1 将分组 checkbox 改为「按分组筛选」模式
- F3.2 勾选分组 = 自动勾选该组下全部终端，允许用户单独增减
- F3.3 终端列表中标注在线/离线状态，方便选择在线终端
- F3.4 配置项下拉列表增加中文说明/分类标签
- F3.5 支持全选/反选操作

#### F4: 首页加载体验优化（P1）
**用户诉求：** 首页状态从"检测中..."闪变为实际状态，产生不安感。

**需求描述：**
- F4.1 首页在线状态 SSR 直接输出或骨架屏展示
- F4.2 减少页面加载后的 "检测中..." 闪烁
- F4.3 搜索框支持分组名搜索
- F4.4 终端列表支持分页（终端数量 > 20 时）

#### F5: 配置对比增强（P2）
**用户诉求：** 对比功能单一，无法导出结果。

**需求描述：**
- F5.1 支持同时对比多个配置项
- F5.2 差异项高亮颜色更醒目
- F5.3 支持导出对比报告（CSV / Markdown / PDF）
- F5.4 表格列宽自适应优化

#### F6: 配置审计与历史（P2）
**用户诉求：** 无法追溯配置变更历史，操作后无法回滚。

**需求描述：**
- F6.1 记录每次配置修改的时间、操作人、变更内容
- F6.2 支持查看配置修改历史
- F6.3 支持一键回滚到上一次配置

#### F7: 终端健康度概览（P2）
**用户诉求：** 当前仅展示在线/离线状态，无法判断配置是否正常。

**需求描述：**
- F7.1 终端概览增加健康度评分指示
- F7.2 展示异常配置项清单
- F7.3 配置版本号异常预警

### 3.3 非功能性需求

| 编号 | 需求 | 说明 |
|------|------|------|
| N1 | 单终端配置操作响应 ≤ 3s（内网环境） | 不含终端 config-serv 处理时间 |
| N2 | 批量 50 台终端推送完成 ≤ 30s | 含并发请求控制 |
| N3 | 支持 ≥ 200 台终端注册 | YAML 配置加载性能 |
| N4 | 保持零外部运行时依赖 | 维持 PyInstaller 单文件 EXE 分发 |
| N5 | 兼容 Windows 10/11 + Windows Server 2016+ | 目标部署环境 |

## 4. 预沟通问题清单

> 请各位 PM 在评审会议前思考以下问题，会议中逐一讨论。

### 4.1 战略层

1. **项目定位**：Config Center 未来是否要承担更多运维功能（如日志查看、终端监控、告警）？还是保持纯粹配置管理的定位？
2. **用户范围**：除当前 5 类用户外，是否还有其他角色需要纳入考虑？
3. **竞品对标**：是否有对标产品可以作为功能参考？

### 4.2 功能层

4. **配置历史与回滚**：F6 的优先级是否应该提前？没有回滚能力是否构成操作风险？
5. **用户认证**：当前无认证机制。是否需要在本次迭代中加入简单的登录认证（如静态 Token 或密码）？
6. **多配置项同时对比**：F5.1 的技术实现较复杂，是否能接受分次操作的折中方案？
7. **JSON 编辑器**：F1 引入 CodeMirror/JSONEditor 会增加打包体积约 1-2MB，是否接受？

### 4.3 技术层

8. **部署维护**：单 EXE 方案是否需要升级为 Windows Service（实现开机自启）？
9. **配置存储**：是否始终维持"只读代理、不存配置"的架构原则，还是考虑加入本地缓存？
10. **终端发现**：当终端超过 200 台时，YAML 静态文件是否够用？是否需要引入简单数据库？

## 1. 需求拆解

### 1.1 拆解方法

采用 **WBS（工作分解结构）** 方法，将项目整体目标逐层拆解为可独立落地的任务单元。每个任务单元满足以下条件：
- **可独立交付**：产出物可单独验证
- **职责清晰**：有明确的责任人
- **可估算**：工作量 ≤ 2 人天
- **有前置依赖**：可识别前置任务

| 迭代一全部 | 迭代二全部 | **时序型** — 迭代一的核心编辑器是迭代二所有功能的基础 |

### 1.4 任务优先级标定规则

| 优先级 | 标定条件 | 处理策略 |
|-------|---------|---------|
| **P0** | 阻断用户核心操作链路，或影响 80%+ 用户的日常使用 | 必须在本迭代内完成，不可延期 |
| **P1** | 严重影响操作效率或用户安全感，或存在数据安全风险 | 优先在本迭代完成，可延期但不超过下一迭代 |
| **P2** | 体验优化类需求，不影响功能可用性 | 按产能分配，可裁减至后续迭代 |
| **P3** | 低频场景或边缘需求 | 视资源情况决定是否纳入 |

### 5.3 代码审查标准

| 审查维度 | 必须满足的条件 | 建议满足的条件 |
|---------|--------------|--------------|
| **正确性** | 逻辑正确，无明显的 off-by-one、空指针、类型错误 | 覆盖了正常的边界情况 |
| **安全性** | 无 XSS、注入风险；用户输入经过校验或转义 | 有基本的安全纵深防御 |
| **可读性** | 变量/函数命名清晰，无魔法数字 | 复杂逻辑有注释说明 |
| **性能** | 无 N+1 查询、无阻塞主线程的 JS 操作 | 大数据量场景有分页或虚拟滚动 |
| **测试** | 新增逻辑有对应的单元测试 | 边界情况也有测试覆盖 |
| **兼容性** | 不影响 PyInstaller 打包流程 | 考虑降级浏览器兼容 |

**审查流程：**
1. 开发者提交 PR → 自动触发 CI（lint + 单元测试）
2. CI 通过后 → 至少 1 人 Code Review
3. Reviewer 提出修改意见 → 开发者修改 → 再次 CI
4. Review 通过 → 合并目标分支
5. **禁止：** 未经 Review 直接合并、CI 失败时合并
